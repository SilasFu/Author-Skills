# 规则分类学与事实源路由字典 (Rule Taxonomy & SSOT Routing)

在执行 `/project-guard evolve` 或处理用户偏好纠偏时，必须依据本字典进行精准分类与权威事实源路由，严禁随意错放。

---

## 1. 规则分类三叉戟判定树 (Decision Tree)

```text
用户提出纠偏/新偏好/经验教训
 │
 ├── 属于个人的长期通用偏好、交互习惯或方法论？
 │    └── 路由到: MY_Memories/knowledge/profile/工作与决策偏好.md (分类: 个人画像/全局偏好)
 │
 ├── 属于界面美学、UI布局、动效色彩、交互状态或组件视觉契约？
 │    └── 路由到: 当前项目 DESIGN.md -> ## 5. 设计规范禁忌 (Do's and Don'ts)
 │
 └── 属于代码结构、单文件行数、技术栈选型、编译器门禁、模块依赖契约？
      └── 路由到: 当前项目 AGENTS.md -> ## 3. 质量与架构禁忌 (Do's and Donts)
```

---

## 2. 分类定义与标准示例

### 分类 A：全局个人偏好与方法论 (Global Personal Profile)
- **特征**：跨项目通用，体现用户的沟通风格、代码整洁偏好、Git 习惯等。
- **落盘权威文件**：`$MY_MEMORIES_PATH/knowledge/profile/工作与决策偏好.md`（或 `MY_Memories/knowledge/profile/工作与决策偏好.md`）
- **示例**：
  - *“我喜欢每一步操作前先列出三条简明计划”* ➔ 追加至 `## 交互与沟通偏好`；
  - *“所有 Git commit 必须使用 Angular 规范”* ➔ 追加至 `## 决策与执行铁律`。

### 分类 B：视觉与设计契约 (Visual & Interaction Design SSOT)
- **特征**：约束前端样式、色彩语义、状态反馈、组件规范。
- **落盘权威文件**：`<project-root>/DESIGN.md` 或 `<project-root>/docs/DESIGN.md`
- **示例**：
  - *“不要用大面积深蓝色，全部改成中性灰”* ➔ 修正 `## 2. 核心色彩体系与语义 Token`；
  - *“弹窗底部按钮必须右对齐，且取消按钮在左、确认按钮在右”* ➔ 追加至 `## 5. 设计规范禁忌 (Do's and Don'ts)`。

### 分类 C：项目工程与架构规范 (Project Architecture & Quality Gates)
- **特征**：特定项目的技术实现门禁、单文件行数、三层垂直切片、构建检查。
- **落盘权威文件**：`<project-root>/AGENTS.md`
- **示例**：
  - *“所有接口调用必须经过 apiClient 单例，严禁直接使用 fetch”* ➔ 追加至 `## 3. 质量与架构禁忌`；
  - *“这个项目测试覆盖率必须达到 80%”* ➔ 追加至 `## 2. 核心架构与代码质量硬门禁`。

## 3. 原子化提取格式 (Atomic Rule Extraction Standard)

提炼新规则时，必须遵循以下结构化表达：

```markdown
- **【触发条件】**：当执行 <具体操作/场景> 时；
- **【强制要求】**：必须 <正向肯定行为描述>；
- **【禁止事项】**：严禁 <具体违规反例>；
- **【验证方式】**：通过 <编译器/测试/视觉检查> 确保 100% 达成。
```
