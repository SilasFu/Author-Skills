# Author-Skills 产品需求与背景规格文档 (PRD)

## 1. 仓库建立起因与核心定位

### 1.1 为什么建立 `Author-Skills` 仓库？（诞生起因）
在过去的多 Agent 协作与跨设备开发中，我们遭遇了以下四大核心痛点：
1. **技能资产分散与易碎**：自研技能直接写在某个 Agent 的私有配置目录（如 `~/.gemini/` 或 `~/.cursor/`），一旦重装电脑或格式化 C 盘，辛苦调试的 Prompt 和规则瞬间丢失；
2. **公版技能与自研技能混杂**：社区技能（如各种网页剪藏、格式转换工具）与个人核心工作区治理逻辑混在一起，缺乏唯一的“原创作者源头仓库（Source of Authoring）”；
3. **过度工程与业务轮子陷阱**：过去容易陷入为轻量需求编写复杂插件（如试图写专有浏览器扩展）的误区，耗费大量精力却偏离了核心母体机制；
4. **Agent 协作跑偏与同一错误反复犯**：对话中给 Agent 提了纠偏要求（如“不要用卡片嵌套”、“单文件不能超 200 行”），换个会话或换个 Agent（Codex / Kimi / Claude）就全部忘光。

**因此，`Author-Skills` 正式确立为：个人 AI 工作区生态的「元治理与自进化母体技能源头仓库」**。它与 `My-Skills`（全量公版技能备份仓库）物理隔离，只专注于机制的建立、自检、自愈与自进化。

## 3. 核心功能规格矩阵

| 技能标识 | 核心定位 | 输入与触发 | 输出与交付物 | 非目标 (Non-Goals) |
| :--- | :--- | :--- | :--- | :--- |
| **`workspace-bootstrap`** | 全生态冷启动与自举 | `/workspace-bootstrap init` 或在新环境首次配置 | 6 大工作区骨架、工作区级 `AGENTS.md` 与 `CLAUDE.md`、环境变量注入、多 Agent 软链接挂载 | 不承担具体项目内部业务代码编写 |
| **`project-guard`** | 项目守护、体检与规则自进化 | `/project-guard init` / `doctor` / `evolve` | 项目级 `AGENTS.md` 与 `CLAUDE.md`、单文件拆分重构、规则回写 Git 提交 | 不替代具体前端脚手架工具 |
| **`workspace-lifecycle-governance`** | 跨工作区流转决策 | 知识缺口感知、新立项诉求、架构决策变更 | `My_Learning` 缺口卡片、复用阶梯决策报告、`MY_Memories` 索引同步 | 不直接编写业务学习文章本身 |
| **`my-memories`** | 权威记忆库查询接口 | 查询画像、偏好、协作边界、架构规范 | 权威 Markdown 上下文切片 | 不作为写入通道（写入由 governance 承担） |

## 4. 关键原则与红线

1. **元治理原则**：本仓库**绝不开发**琐碎的业务功能、任务拆解或特定 UI 布局代码（此类需求交给公版社区 Skill）；
2. **零隐私与中立性**：源码中 100% 杜绝个人姓名、私密路径与特定 GitHub 账号硬编码；
3. **防早退门禁**：所有 SOP 必须具有明确的客观可检验完成标准（Checkable Bounds）。
