# 四级立项复用阶梯决策手册 (Reuse-Ladder Matrix & Heuristics)

为防止个人生态陷入“每有一个想法就新建一个 Git Repo”的碎片化陷阱，任何新需求在立项前**必须严格按顺序自顶向下匹配四级复用阶梯，命中即止**。

---

## 1. 四级复用阶梯架构表

```text
新需求 / 新想法进入
 │
 ├── [Level 1] 现有工具/CLI/MCP 可直接满足？ ────────────► 结论: 配置使用 (Zero Code)
 │
 ├── [Level 2] 与现有项目共享技术栈/用户/运行时？ ────────► 结论: 作为存量项目 Module/Adapter 扩展
 │
 ├── [Level 3] 属于跨项目 Agent 规则/机制进化？ ──────────► 结论: 回写 Author-Skills / MY_Memories
 │
 └── [Level 4] 独立立项资格审查 (需同时 100% 满足 4 项硬门禁) ─► 结论: 授权在 Vibe_Coding 新建仓库
```

---

## 2. 独立立项资格审查四大硬门禁 (The 4 Hard Gates)

只有在 Level 1、Level 2、Level 3 均无法满足时，方可进入 Level 4 资格审查。必须**同时满足全部 4 项硬门禁**，缺一不可：

| 门禁项 | 核心判定标准 | 违规/未通过时的反模式与后果 |
| :--- | :--- | :--- |
| **1. 独立用户心智** | 具有完全独立的产品定位、目标受众与独立发布生命周期。 | 将现有系统的一个普通子功能误当做新产品独立建库，导致维护成本陡增。 |
| **2. 运行时物理隔离** | 技术栈或宿主运行时存在物理冲突（如桌面 GUI 客户端 vs 嵌入式 Daemon 服务），合并会导致严重依赖污染。 | 盲目为了“解耦”将两个同一技术栈的前端项目拆分为两个仓库，导致公共类型与组件重复编写。 |
| **3. 外部参考库查重** | 已在 `Reference_Coding` 中确认无现成可用模式或成熟实现。 | 重复发明外部开源社区早已解决的轮子。 |
| **4. 最小 PoC 验证** | 核心机制与架构风险已在 `My_Learning` 或原型中验证通过。 | 盲目建立空仓库，写了三行代码后因可行性问题废弃，产生大量“僵尸仓库”。 |

## 3. 常见典型场景判别字典

- **场景 A**：“我想做一个从 YouTube 下载视频并提取字幕的工具。”
  ➔ **判别**：直接利用 `yt-dlp` 与 `ffmpeg` CLI 脚本，命中 **Level 1**（Zero Code）。
- **场景 B**：“我想给现在的 React 仪表盘添加一个导出 PDF 报表功能。”
  ➔ **判别**：命中 **Level 2**（作为现有项目的扩展组件或 Hook，严禁新建仓库）。
- **场景 C**：“我想让 Agent 以后在写代码时都遵循某种新的注释规范。”
  ➔ **判别**：命中 **Level 3**（回写 `Author-Skills/project-guard` 与 `MY_Memories`）。
- **场景 D**：“我要开发一个全新的本地文件全文语义索引 Daemon 服务（Rust 实现，与现有 Web 前端运行时完全独立，且已完成核心 PoC）。”
  ➔ **判别**：4 大门禁全部 PASS，命中 **Level 4**，授权在 `Vibe_Coding/` 建立独立仓库！
